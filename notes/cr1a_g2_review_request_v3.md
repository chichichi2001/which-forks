## 直し方（前回の「簡易の fail-closed 運用」の案を取った）

- **自動の引き継ぎをなくした**：記録には持ち主のランタイムの番号（と epoch）が入る。古さに関係なく、別のランタイムは止まる。オーナーが前のランタイムが止まっていることを確かめ、その番号を `OWNER_CONFIRMS_OLD_RUNTIME_STOPPED` に入れたときだけ引き継ぐ（epoch を 1 上げる）。同じ VM のカーネル再起動は、`/content` に残した同じ番号なので引き継ぎ不要。
- **送る前の見張り（鍵ではない）**：保存のたびに世代番号を 1 上げる。ループの各回の最初と、毎回の `create()` の直前に Drive の記録を読み戻し、持ち主・epoch・世代番号が自分の最後に書いたものと違えば、送らずに止まる。Drive に比較交換はないので、これは原子的な鍵ではなく、別の書き手を見つける見張りであることをコードとノートブックに書いた。「自動で二重実行を防げる」とは書いていない。
- **試験**：A が回している記録に B が来ると（古さに関係なく）止まる／番号違いの確認では止まる／オーナーの確認で B が引き継いだあと、古いメモリの A が戻っても何も送らない／同時に始めて B があとから書いたとき、A は送る前に止まる／2 回目と 3 回目の `create()` のあいだに別の書き込みがあると 3 回目を送らない。
- **入力 600（止めない指摘）**：G1 からの目安に加えて、各問題のいちばん長いプリフィル（c = L）の入力を API のトークン数え（無料）で数え、600 を超えたら送らない。
