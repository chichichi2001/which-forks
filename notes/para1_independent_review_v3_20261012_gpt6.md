## Blocking findings — 火力強め、ただし新しく修理した箇所だけ

### R1/P1-B1 — 「空の基準語 w は位置ごと除外」と \`classify_candidate\` の実行順が矛盾する

**根拠:** 計画書 **46–49行、135–144行**は、wが英数字なしの位置なら **\`EXCLUDED_EMPTY_TARGET\` として位置ごと除外**（Bでは 3 番を空のw除外に充てる）と読む。一方、\`scripts/para1_typing.py\` の \`Typer.classify_candidate\` は以下の順：

\`\`\`python
if special: return "特別", ""
if "\ufffd" in piece: return "バイト片", ""
w = normalize(w_raw)
if is_empty(w): return "EXCLUDED_EMPTY_TARGET", ""
\`\`\`

従って人工例 \`w="..."\` で **special=True** または **piece="�"** の場合、同じ位置を「特別」「バイト片」と数える。一方、既存の **G0b B17 は通常の候補 \`" cat"\` のみ**で、w空との重なりを検査していない。

**最小修理:** 計画の「位置ごと除外」を正とするなら **w空判定をclassify_candidateの最初に移す**（またはcallerで位置を全候補一律除外し、関数に決して空wを渡さない明文の契約とチェックを設ける）。G0bに \`w="..." , special=True\` と \`w="..." , piece=U+FFFD\` を加える。保存される mass/件数からこの位置を全カテゴリと分母から一貫して外すことまでテスト。

### R1/P1-B2 — 実トークナイザー復号と \`starts_ws\` の整合性が仕様にはあるが試作上未完成

**根拠:** 計画 **127–133, 199–204行**で、\`convert_ids_to_tokens\` の \`Ġ\` / \`▁\` / \`Ċ\` やバイト復号の取り扱いを指定し、両モデルの実トークナイザーに固定文を通したroundtripをG0bで要求した。一方、現試作コードの\`classify_candidate(piece, starts_ws, special, w)\`は **デコード機能を持たず、\`starts_ws\` をcallerから独立な真偽値として受け取る**。17のG0bは手書きの \`piece\` と \`starts_ws\` の一貫した組を渡しているだけで、実ID→文字列→判定を監査していない。

Byte-level BPE/SentencePieceでは単独tokenの表現と連結後のデコードが一致するとは限らない。\`Ġ\` / \`Ċ\` の単純置換のみで全Unicodeの字面と改行を復元できる保証はない。**これは「現在の17例が誤り」という指摘ではない**。現コードとG0記録から、実トークンの分類が規則どおり実装可能であることは未証明。

**最小修理:** モデルごとの可逆な**byte-level復号手順**をAPI/版に固定するか、\`tokenizer.decode([id], clean_up_tokenization_spaces=False, skip_special_tokens=False)\`などの採用条件と**単体/連結不一致時の規則**を明記する。\`starts_ws\` と \`special\` はdecoder内部でtoken IDから求める。G0bに非ASCIIとbyte断片、改行、空白が連続する文を加え、ID→文字列→語頭フラグ→分類の end-to-end checkを凍結後G0ではなく**実装直後の事前スモーク**としても行う。実施結果が無い現時点では tokenization correctness をPASSと記録しない。

### R3/P3-B1 — 「ずらした比較」の標本空間とG0cの偽陽性ゲートが固定されていない

**根拠:** 計画 **70–81行、94・105–107行**。同一問題・同じ層で切れ目単位の\`w\`をずらす方針と、観測−baselineの問題平均・cluster bootstrapは明確になった。ただし、**同一層の別位置へ1対1で置換する置換（derangement）なのか、別位置を重複ありで独立抽出するのか、元の場所への一致をどのように禁止するのか**が未指定。違う方式では w の周辺分布および期待割合が変わる。例えば層内2位置は必ず交換できるが、独立抽出なら同じwの複数回割当ても起こる。

G0cの世界は \`a\`をwと独立に同層から選ぶが、**実際の部AはCR-1定義10の前方一致で「同じ語」の続きが先に除外される**（計画 **85–90行**）。この選択操作を人工世界で再現しない場合、人工生成時にはaとwが独立でも **抽出後の(a,w)は必ずしも独立ではない**。そのため200世界中0.075以下という通過率は、実際の条件付きA2の偽陽性校正を保証しない。人工語彙表の固定ハッシュ、サンプリング分布・乱数の消費順、200世界×2,000ずらしの生成法も未指定。

**最小修理:** 同じ問題/層の eligible 位置集合を確定し、**元位置を含まない一対一置換（uniform derangement等）**または別の明示的分布を決め、1位置以下は除外。ソート順・乱数種の派生・乱数の消費順を明記。G0cに**CR-1のprefix抽出、空w除外、同位置クラスタで反復応答、A2の各停止条件**をそのまま通すことを必須にする。人工生成の基底分布は固定語彙表のSHAと共に記録。これができないなら **A2を完全に記述-only（ラベルなし）に下げる**のが最小の安全策。\`_MISMATCH_BASELINE\`という名称自体と「偶然とは言わない」というscopeは **PASS**。

### R4/P4-B1 — G3の \`AUDIT_LOGIT_DRIFT\` が保存設計から判定不能（明白な工程矛盾）

**根拠:** 計画 **157–161行**は、保存する本番結果を「上位1000の候補IDと確率、各サンプラーのK内真偽、正規化分母、M,tail」と指定し、**元の全語彙float32 logitは保存しない**。しかし **207–212行**のG3は、取り直した全語彙logitと**本番の全語彙logit**の最大絶対差を計算し、\`>1e-4\`なら\`AUDIT_LOGIT_DRIFT\`とする。

**元の全語彙logitがなければ、この最大差は求められない。** 一部の確率と集合サイズからは元のfloat32logit全体を復元できないし、softmaxは共通シフトに不変なので、元の生logitとの全語彙最大差は数学的にも識別できない。従って\`AUDIT_LOGIT_DRIFT\`を正しく判定する実装経路が存在しない。

**最小修理:** 
- **案A:** G3対象の5%の問題について、本番実行時に元の **全語彙float32logitを監査用に保存**（対象問題を事前にSEED_PARA_AUDITで固定し、G2前に宣言）。新logitと比較してdriftを判定し、許容内なら旧保存値と再計算の一致も検証する。 
- **案B:** 全語彙生logitの最大差という指標を捨て、**本番時に保存した同一候補集合の順位・確率・M・tailとの測定値差**をdrift判定に使う。ただしこちらは未保存候補での相違を検出できないので、「全語彙logit一致」や独立K再構築の証明とは呼ばない。
- 重要: drift検知時に、取り直したlogitで参照実装とGodPorkを比較して**一致しただけ**では、**本番時に保存した数値が正しいことは証明できない**。その場合は本番データの採択/保留/ラベル抑制を明文で決める。例えば\`AUDIT_LOGIT_DRIFT_NO_CONFIRMATORY_VERDICT\`等。
